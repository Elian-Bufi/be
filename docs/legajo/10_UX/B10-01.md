# 0. Objetivo del bloque

Definir la **arquitectura de navegación principal de BE** antes de diseñar pantallas detalladas.

Este bloque responde:

- qué superficies existen;
- qué actores usan cada una;
- cuál es la home de cada actor;
- cómo se entra a un asesorado;
- cómo se mantiene el contexto;
- cómo se vuelve;
- qué rutas pertenecen a Website;
- qué navegación pertenece a APK;
- qué rutas son públicas;
- cómo se evita mezclar profesional, asesorado y administrador;

# 1. Problema estructural que se elimina

El AS-IS previo mezclaba:

```text
login
→ dashboard común
→ shell profesional
```

aunque el actor fuera asesorado.

El TO-BE prohíbe esa arquitectura.

Regla:

```text
IDENTIDAD AUTENTICADA
→ RESOLUCIÓN DE CONTEXTOS LEGÍTIMOS
→ SHELL CORRECTO
→ HOME CORRECTA
```

Nunca:

```text
login
→ misma home
→ esconder botones
```

# 3. Principio de contexto

Una **identidad BE** puede poseer más de un contexto legítimo.

Ejemplo:

```text
misma identidad
├─ contexto asesorado
└─ contexto profesional
```

No se fusionan las experiencias.

Regla:

> **El contexto activo determina shell, navegación y capacidades visibles, pero nunca sustituye autorización server-side.**

---

# 4. Decisión candidata central — selector explícito de contexto

## `CAND-10-CTX-A`

Cuando una identidad posee **un solo contexto operativo**:

```text
login
→ entrada directa
```

Ejemplo:

```text
solo asesorado
→ Hoy
```

Cuando posee **más de un contexto legítimo**:

```text
login
→ último contexto válido
```

con un **selector explícito y siempre localizable** para cambiar.

No se propone una pantalla obligatoria de selección en cada login.

Razón:

- reduce fricción;
- evita mezclar shells;
- permite cambio consciente;
- mantiene contexto persistente.

### Regla de seguridad

Cambiar contexto:

```text
NO otorga permisos
NO eleva rol
NO cambia identidad
```

Solo cambia la superficie desde la que el actor opera.

# 20. Deep links

Los deep links autenticados deben recuperar contexto.

Ejemplo conceptual:


- el ID de UI no concede autorización;
- la aplicación resuelve contexto;
- si no puede revelarlo, muestra estado neutral;
- no redirige a otra persona;
- no filtra que existe.

# 24. Cambio de contexto

## Si hay dos contextos legítimos

Componente global:

```text
Context switcher
```

Ejemplo:

```text
Trabajando como:
Profesional
```

Opciones:

```text
Profesional
Asesorado
```

Al cambiar:

```text
PRO → ADV
```

se reemplaza completamente:

- shell;
- navegación;
- home;
- memoria de navegación contextual.

No se conservan abiertos datos del otro contexto.

# 25. Persistencia del contexto

Candidato:

```text
último contexto usado
```

puede persistirse local/server-side de forma no sensible.

En próximo login:

```text
si sigue siendo válido
→ usarlo

si ya no es válido
→ resolver contexto disponible
```

No se guarda un “rol autorizado” en cliente como fuente de verdad.

# 29. Estados de acceso y navegación

La UI diferencia:

## `NO_DATA`

El actor puede ver la categoría pero no hay datos.

## `NOT_AVAILABLE`

La categoría puede revelarse pero no está operativa/disponible.

## `PARTIAL_VIEW`

La vista se construyó con subset autorizado.

## `RESOURCE_NOT_AVAILABLE`

Estado neutral para deep link no revelable.

Evitar:

```text
"No tenés permiso para ver el plan de Juan"
```

si confirmar `Juan/plan` no es legítimo.

- revisar información simple;

# 35. Errores y redirecciones de rutas

## No autenticado

Ruta protegida:

```text
→ login
```

con retorno seguro a la intención original si sigue siendo válida.

## Contexto incorrecto

Ejemplo:

asesorado abre `/pro/caseload`.

No mostrar:

```text
403 PROFESSIONAL_REQUIRED
```

como pantalla técnica.

Tratamiento candidato:

```text
si posee contexto PRO
→ ofrecer/cambiar contexto explícitamente

si no
→ volver a su home válida
```

sin revelar capacidades inexistentes o datos sensibles.

## Recurso no revelable

```text
→ estado neutral
→ acción "Volver"
```

# 36. Navegación offline — APK

P0 no promete offline completo.

Pero navegación mobile debe soportar:

```text
sin conexión
→ shell sigue estable
→ estado claro
→ retry
```

Una acción sensible no se muestra como completada si el servidor no confirmó.

Idempotency del 09 protege reintentos, pero la UX debe mostrar:

```text
enviando
confirmado
no confirmado / reintentar
```

# 39. Riesgos encontrados

## `R10-B01-01 — Multi-contexto`

Si una identidad puede ser profesional y asesorado, un cambio implícito de shell puede provocar errores graves de contexto.

Control:

```text
selector explícito
+
shell claramente diferenciado
```

## `R10-B01-02 — Tabs como revelación`

Mostrar un tab porque “hay datos” puede filtrar existencia.

Control:

```text
mostrar tab por capacidad/autorización de categoría
NO por existencia oculta del dato
```

## `R10-B01-03 — Deep links`

Una URL copiada puede revelar nombre/estado si la pantalla renderiza antes del PDP.

Control:

```text
neutral loading
→ resolve
→ render
```

## `R10-B01-04 — Dashboard universal`

Recrear `/dashboard` como centro de todos los actores repetiría el defecto legacy.

Control:

```text
home contextual
```

# 40. Criterios que 11A deberá probar

1. asesorado nunca entra al shell profesional;
2. profesional nunca entra a APK como si fuera asesorado sin cambio de contexto;
3. admin no obtiene navegación a datos de asesorados;
4. un contexto revocado deja de ser seleccionable;
5. deep link no revelable no filtra nombre ni dominio;
6. tab oculto no depende de existencia sensible;
7. pausa/finalización corta contenido profesional;
8. `partialView` se representa sin revelar lo oculto;
9. back-navigation conserva contexto;
10. context switch limpia memoria visual sensible del shell anterior;
11. offline/retry no produce falso éxito;
12. direct URL no salta onboarding/verificación requerida.
